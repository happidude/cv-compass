# Database persistence foundation

The `com.cvcompass.backend.ingestion` module organizes the five POC entities in
`ingestion.entity`, plain Spring Data repositories in `ingestion.repository`,
and status/method enums in `ingestion.enums`. It remains one ingestion module;
no services, controllers, custom queries, or named interfaces are added.

Mappings use explicitly quoted uppercase table/column names, `Long` identity IDs,
`Instant` timestamps, and Hibernate `@JdbcTypeCode(SqlTypes.JSON)` for JSONB.
`BaseEntity` is an abstract `@MappedSuperclass` providing `ID` and `CREATED_AT`
for all five entities. `UpdatableEntity` adds `UPDATED_AT` and is used only by
`Candidate`, whose table contains that column. Future entities select the base
matching their actual schema; the mapped superclasses create no tables or modules.
Identity and creation time are read-only through the entity API.
Creation timestamps are generated by PostgreSQL. Candidate `UPDATED_AT` must be
set by the application on subsequent changes. Relationships are unidirectional,
lazy, and have no cascading persistence/deletion. The extraction references its
job by primary key; V2's composite FK independently enforces that both references
identify the same document.

## Configuration

Application datasource, Flyway, and profile configuration are unchanged. Both
profiles retain `ddl-auto: validate`, and Spring Boot supplies transaction
management through JPA auto-configuration. Flyway owns schema changes.

Gradle tests use UTC to avoid host timezone aliases rejected by PostgreSQL JDBC.
No application dependency or infrastructure changes are required.

## CI and constraints

The `Persistence CI` GitHub Actions workflow runs Java 25 and `./gradlew check`
with a disposable PostgreSQL 17 service and a dedicated `cv_compass_ci` database.
Its credentials are CI fixtures only. Each integration class still owns a unique
schema inside that database. The workflow runs on pull requests to main, pushes
to main, and manual dispatch; it requires no production secrets.

Constraint tests cover counter totals, negative retry counts, malformed SHA256,
invalid statuses (using JDBC to bypass Java enum validation), every foreign key,
and extraction/job document consistency. Each rejected statement runs in its own
rolled-back test transaction; no subsequent query uses an aborted transaction.

## Persistence considerations for Milestone 2

`UPDATED_AT` remains application-managed. Application code must explicitly set it
when changing a candidate, preferably using a UTC Clock in future services.
No entity callbacks or automatic auditing have been introduced. Integration tests
verify updates retain the identity and database-generated creation time.

Concurrent batch completions can lose increments if separate transactions load
the same counters and save independently: CHECK constraints protect value ranges,
not lost updates or duplicate completion notifications. Before concurrent job
processing is implemented, choose transactional atomic counter updates or an
approved optimistic/pessimistic locking strategy, make job completion idempotent,
and update counters and derived batch status consistently in one transaction.
No batch processing or locking is implemented in this foundation PR.

# Milestone 2: Backend application foundation

## Packages and module boundaries

```text
com.cvcompass.backend
|-- BackendApplication
|-- ingestion                 (cohesive POC business/persistence module)
|   |-- entity                (JPA entities and mapped superclasses)
|   |-- enums
|   `-- repository
`-- web                       (HTTP infrastructure module)
    |-- ApiResponse           (optional success envelope)
    |-- ApiError               (standard error contract)
    |-- FieldViolation
    |-- error                 (internal MVC advice)
    `-- logging               (internal correlation filter)
```

Spring Modulith discovers `ingestion` and `web` as closed modules. `web` declares
no allowed dependencies on application modules. Its root records are its public
API; exception handling/filter implementations remain internal. Ingestion stays
cohesive because document, candidate, job, and extraction mappings share direct
JPA relationships. There is no cross-module entity access, new candidate module,
or worker module. Future controllers can use the web contracts; extracting new
business modules requires a separate architecture decision. Architecture tests
verify both module discovery and `ApplicationModules.verify()`.

## HTTP contracts

No production demo or business endpoints are added. Controllers may return DTOs,
`ResponseEntity`, or an optional `ApiResponse<T>` (`{"data": ...}`), as appropriate.
There is no automatic wrapping; 204 responses retain an empty body.

MVC errors have this shape:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Invalid request",
  "correlationId": "example-request-123",
  "details": [
    {"field": "label", "message": "must not be blank"}
  ]
}
```

`details` is empty when no field-level validation applies. Correlation ID is null
only when handling occurs outside the correlation filter. Validation uses request
DTOs and Jakarta Bean Validation; the test-only controller demonstrates `@Valid`,
`@NotBlank`, `@NotNull`, `@Size`, nested values, and method parameter validation.
Rejected values are never included in error metadata. Validation messages should
remain generic and must not interpolate sensitive request values.

The advice extends Spring MVC's `ResponseEntityExceptionHandler`, preserving
framework status codes and headers (including `Allow` for 405). Standard cases:

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | Bean Validation failure, with field details |
| 400 | INVALID_REQUEST_BODY | Missing, malformed, or unreadable JSON body |
| 400 | INVALID_REQUEST | Invalid/missing request parameters and other bad requests |
| 404 | NOT_FOUND | Missing handler/resource |
| 405 | METHOD_NOT_ALLOWED | Unsupported method |
| 406 | NOT_ACCEPTABLE | Unsupported response representation |
| 413 | PAYLOAD_TOO_LARGE | Request exceeds supported size |
| 415 | UNSUPPORTED_MEDIA_TYPE | Unsupported input content type |
| other 4xx | REQUEST_ERROR | Framework status preserved, generic reason |
| 5xx | INTERNAL_ERROR | Generic server failure without internal details |

Unexpected failures log their exception class and stack locations, with the MDC
correlation ID. Exception messages and causes are intentionally excluded because
they can contain SQL, credentials, request content, or personal data. API errors
never include stack traces, exception names, SQL, or raw framework exception
messages. No request/response body or authorization header logging is introduced.

## Correlation IDs and logging

A servlet filter accepts one `X-Correlation-ID` header matching
`[A-Za-z0-9][A-Za-z0-9._-]{0,63}` (1-64 ASCII characters). Missing, duplicate,
blank, oversized, non-ASCII, or otherwise invalid IDs are replaced with a UUID.
The ID is stored in a request attribute and MDC `correlationId`, included in the
response header, and included in standardized error responses. The log level
pattern displays it. The filter removes its MDC key in `finally`, including when
the downstream servlet throws, and preserves unrelated MDC entries.

This is synchronous request correlation. Propagating MDC into future executor,
async servlet, or worker tasks is not implemented. Correlation IDs are diagnostic
identifiers supplied by clients, not trusted identity or authorization claims.
The advice covers MVC dispatch errors; container/network failures outside MVC
and future security filter errors need their own integration when introduced.

## Module and contract

The closed storage Modulith module exports FileStorageService, StorageKey,
StoredFile, and StorageException at its root. storage.local and storage.config
are internal; storage declares no application-module dependencies.
It has no ingestion, web, JPA, multipart, or PDF dependency. Future application
services use constructor injection of FileStorageService, never the adapter.

| Operation | Contract |
| --- | --- |
| store(InputStream) | Streams from the current position to EOF. Caller owns and closes the input even on failure. Generates a new key; returns actual byte size and lowercase SHA-256 after publication. |
| read(StorageKey) | Opens a caller-owned InputStream; use try-with-resources. Missing objects raise NOT_FOUND. Open failures raise StorageException; subsequent stream reads/close can throw IOException. |
| delete(StorageKey) | Idempotent when absent; other failures raise DELETE_FAILED. |
| exists(StorageKey) | False only when absent; errors raise READ_FAILED. |

Keys are opaque, case-sensitive 32-character lowercase hex identifiers. This is a
storage contract, not a filename, absolute path, provider name, or content hash.
Callers persist key.value() and reconstruct with new StorageKey(value).
Invalid values raise INVALID_KEY without echoing the supplied key. No caller-chosen
write key, original filename, or metadata persistence is accepted by the adapter.
Empty files and arbitrary binary content are supported. There is no whole-file
byte array: production copying uses a fixed 64 KiB buffer and incremental SHA-256.

StorageException has a small reason enum (INVALID_KEY, NOT_FOUND, UNAVAILABLE,
WRITE_FAILED, READ_FAILED, DELETE_FAILED), safe summary messages, and internal
technical causes. Do not expose/log causes to clients: OS exceptions may include
absolute paths. There are no new HTTP-specific error mappings.

## Configuration and DI

Explicit configuration is required in every environment:

~~~yaml
cv:
  storage:
    provider: ${CV_STORAGE_PROVIDER:}
    local:
      root-directory: ${CV_STORAGE_ROOT:}
~~~

Set CV_STORAGE_PROVIDER=local and CV_STORAGE_ROOT to a private, absolute,
normalized storage directory outside any Git checkout. There is no machine-specific
path or automatic production fallback. Missing/blank settings, relative paths,
filesystem roots, linked ancestors, roots inside a Git checkout, or unsupported
providers prevent startup with an actionable configuration summary.

StorageConfiguration uses validated configuration properties and
@ConditionalOnProperty to select one FileStorageService bean. Only local is
implemented. Provider-specific root configuration stays inside the local adapter
package. No factories, service locators, cloud configuration, or SDKs are added.

## Local filesystem security and reliability

Use a dedicated local volume/directory controlled exclusively by the application
service account and trusted operators. Restrict all ancestor directories against
untrusted replacement. On POSIX, a new root is owner-only (0700); existing roots
must have owner rwx and no group/other permissions. On Windows, provision and
verify an NTFS ACL that permits only the service account and trusted administrators;
the adapter does not provision or comprehensively audit Windows ACLs.

The adapter rejects malformed keys, existing symlinks/reparse-point directories,
nonregular objects, and linked root ancestors. Reads open with NOFOLLOW_LINKS.
**OS access control is a required security boundary:** Java path checks cannot
prevent a hostile local writer from racing directory replacement, changing files,
or injecting hard links. Do not share the root with untrusted writers. This
limitation applies to Windows and POSIX. Untrusted request keys alone cannot
select paths or escape the managed root.

The root is initialized at startup, creating missing directories. Startup probes
hard-link support and create-if-absent behavior. Objects use a flat layout in this
POC. Files are streamed to private .write-*.tmp files, forced to disk, then
published via an atomic non-overwriting hard link in the same directory. Readers
can access only complete, published key names. Existing targets (even on a UUID
collision) are never replaced. Concurrent stores have separate staging files and
generated keys. There is no unsafe copy/move fallback: filesystems without hard
links are rejected, including providers/shares that cannot offer the guarantee.

Ordinary I/O failures retain causes and attempt staging cleanup. Cleanup failures
are suppressed on the original cause. A staging cleanup failure after publication
triggers best-effort rollback of the published key and reports failure, not success.
Do not treat a failed operation as proof that no file remains when the filesystem
also refuses cleanup.

File content is forced before publication, but directory fsync and transactional
durability across power loss are not portable here. A process/power failure may
leave staging files or a published object whose metadata was never returned.
There is no automatic scavenger, backup task, migration task, or file/database
transaction. Trusted operators should inspect stale staging files only while
writers are stopped and use an approved recovery procedure. Do not delete active
staging files. Retain and back up both the object volume and database metadata,
coordinate backups, and test restoration. No CV file contents are logged.

## Future providers and existing document metadata

A future S3-compatible adapter can implement the same streaming interface and
extend conditional configuration without changing business code that depends
only on FileStorageService. It must preserve missing/delete/write semantics and
the stable key contract. No cloud provider is currently selectable.

CV_DOCUMENTS.STORAGE_PATH is TEXT and can later hold the opaque key string rather
than an absolute local path; FILE_SIZE and SHA256 can hold returned metadata.
No mapping/schema or existing data is changed in this milestone. Previously stored
paths must not be assumed to satisfy the new key grammar.

Changing the selected provider **does not migrate existing objects** or preserve
access to local files. Before a future switch, choose either a coordinated complete
migration (copy, verify checksum/size, update existing metadata where needed, then
switch) or an explicitly designed per-object provider identity/routing scheme.
Mixed providers could require approved schema/contract changes; keys alone do not
identify which backend holds an object. S3/MinIO SDKs and migration tools are deferred.

# Milestone 4: Single CV upload

M4 now covers one independently uploaded CV per request and metadata lookup only.
Batch management is handled separately by M5 (PR #6). M4 creates no fake batches,
processing jobs, OCR,
candidate creation, file download, ZIP import, or additional storage providers.

## API contract

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| POST | /api/documents | multipart/form-data, exactly one file part named file; no additional parts or parameters | 201, Location header and DocumentMetadata |
| GET | /api/documents/{id} | Positive numeric document ID | 200 and DocumentMetadata; missing ID returns 404 |

Example (run against a locally configured application):

~~~sh
curl -i -F "file=@/path/to/cv.pdf" http://localhost:8080/api/documents
curl -i http://localhost:8080/api/documents/123
~~~

Success response (illustrative values):

~~~json
{
  "id": 123,
  "originalFilename": "cv.pdf",
  "sizeBytes": 2048,
  "mimeType": "application/pdf",
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "status": "PENDING",
  "createdAt": "2026-10-15T00:00:00Z"
}
~~~

Responses contain neither storage keys nor physical paths. Names are display-only:
client directory components are stripped; blank/control/format-character names and
names exceeding 255 UTF-16 units are rejected. Physical identifiers are generated
only by FileStorageService. Client MIME, declared file size and checksum are not
used to create metadata. Extra checksum/size fields are rejected.

Errors reuse ApiError with correlationId and empty details:
400 for invalid multipart, empty files, invalid filenames or IDs; 413 for size
limits; 415 for invalid PDF signatures/trailers; 404 for missing documents;
generic 500 for storage/database failures. The servlet-level 413 code is
PAYLOAD_TOO_LARGE, while the independent application guard reports FILE_TOO_LARGE.

## Validation and streaming

The file limit is exactly 10 MiB (10,485,760 bytes, Spring's 10MB setting).
Multipart total request limit is 11 MiB to allow framing overhead; additional
parts remain forbidden. A zero multipart file-size-threshold spools file content
to the servlet's temporary directory instead of keeping the entire file in RAM.
Provision writable private temporary storage with sufficient disk space.

The application independently counts bytes while the storage adapter consumes a
borrowed stream, rejecting the first byte above the limit. Actual size and SHA-256
come only from the successfully published StoredFile result.

Content checks require a header at byte zero identifying PDF 1.0-1.7 or 2.0 and
a %%EOF marker followed only by PDF whitespace within the final 1024 bytes.
Validation occurs before publication, including EOF checks during storage reads,
so rejected streams leave no successful object. A fixed-size buffer/tail is used;
production does not call MultipartFile.getBytes() or readAllBytes().

These checks identify the supported PDF signature/trailer profile, not structural
PDF validity, malware safety, encryption support, or OCR readability. Damaged or
hostile PDFs with plausible markers may still be rejected by a future processor.
Full parsing/extraction and scanning are outside M4; no PDF SDK is introduced.

## Transaction and compensation

CvDocumentService depends on FileStorageService and CvDocumentRepository through
constructor injection. Its upload method stores the file outside a database
transaction. A TransactionTemplate with REQUIRES_NEW then persists metadata and
completes its own commit before upload returns. This also avoids accidentally
joining an outer transaction whose later rollback could orphan the file.

Both insert/flush and commit failures are caught outside the transaction boundary.
The service deletes the newly stored key on failure. If compensation fails, the
original failure is retained, the cleanup error is suppressed, and an error log
includes the opaque key, cleanup exception type, and existing MDC correlation ID
for operator recovery. No original filenames, contents, SQL messages, or absolute
paths are logged by this code.

Storage and PostgreSQL remain separate resources. Process death and uncertain
commit outcomes caused by lost database connectivity cannot be made atomic here.
Operators must reconcile orphan objects or inconsistent records after such events;
no background cleanup service or distributed transaction is introduced.

## Schema and migration

V3__allow_standalone_cv_documents.sql drops only NOT NULL on CV_DOCUMENTS.BATCH_ID.
The batch foreign key and existing links remain intact. The JPA association is
nullable. Existing V1/V2 migrations are unchanged; new uploads leave batch and
candidate null, status PENDING, and create no processing jobs. PENDING describes
an uploaded document awaiting future processing, not a successful OCR operation.

## Limits and validation

`CV_BATCH_MAX_FILES` defaults to 10 (allowed 1–10), and
`CV_BATCH_MAX_FILE_BYTES` defaults to 10485760 (allowed 1–10485760). Invalid values
fail startup. The single upload limit remains exactly 10 MiB independently.
BatchMultipartConfiguration derives both servlet parser ceilings from
`max(10 MiB, maxFiles * maxFileBytes) + 1 MiB`, defaults to 101 MiB, and always
spools files to disk (threshold zero). Do not separately override servlet limits;
this bean is authoritative. Tomcat has a finite 101 MiB swallow budget to deliver 413
for moderately oversized chunked requests; a client sending beyond that drain budget
may observe a connection reset. Parser file ceiling deliberately equals request ceiling
so an individually oversized file below the request ceiling can be recorded as an
independent failure. Application streaming validation enforces each actual limit.
The M4 endpoint still rejects duplicate/extra parts and uses PAYLOAD_TOO_LARGE
for declared oversized parts, with its independent FILE_TOO_LARGE stream guard.

Only file parts named `files` are accepted in a batch, with no text parts or query
parameters. Parsing, count and structure validation finish before batch creation.
A malformed or oversized total request creates no batch. Files are processed in
request order, one at a time, with bounded streaming buffers; no production whole
file byte array, ZIP, OCR, queue, scheduler or background execution is used.
A valid request's TOTAL_FILES includes every received file, including rejected PDFs.
These limits bound each request, not aggregate disk/concurrency usage. Provision
private servlet temp storage and local object storage accordingly.

## Persistence, errors and recovery limits

V4 adds CV_IMPORT_ITEMS with batch FK, positive one-based FILE_ORDER unique within
batch, safe DISPLAY_NAME, nullable document FK and ERROR_CODE. Exactly one of
DOCUMENT_ID / ERROR_CODE must be set. Failed files have no document placeholder.
V1–V3 are unchanged; CV_IMPORT_BATCHES already exists and retains its status enum.

The initial PROCESSING batch commits independently. Storage uses M4 validation
and compensation outside DB transactions. For each success, document + batch link
+ item + counter (and final status/time when appropriate) commit in one REQUIRES_NEW
transaction. Failure item + failed counter + final state also commit together.
There is one writer per batch and no API that resumes or mutates an existing batch.
No transaction spans the file stream. Final counters sum to TOTAL_FILES and status
is COMPLETED / PARTIAL_FAILED / FAILED for all / some / zero successful imports.
These counters describe file ingestion, not OCR.

Validation, input I/O and individual storage write failures are recorded and the
next file continues. Storage UNAVAILABLE and DB/transaction errors abort with 500;
previously committed successes remain. If DB cannot record a failure, no result is
fabricated. An aborted batch may remain PROCESSING with fewer items than total;
GET exposes the committed subset. The POST may fail without delivering its batch
ID; operators can inspect the batch list. Retrying POST creates another batch and
can duplicate files; there is no idempotency or automatic retry.

M4 compensation deletes the new object after insert/flush/commit failure; cleanup
failure preserves the primary error and emits the existing safe recovery log.
Connection loss around commit can leave an unknown commit outcome: compensation
may delete an object whose DB transaction actually committed. Process death can
leave staging/orphan files or PROCESSING batches. There is no crash recovery,
reconciliation scheduler, or distributed atomicity guarantee. Trusted operators
must inspect and reconcile database/object storage after those failures.

# Backend package organization after M5

The application keeps exactly three Spring Modulith modules: ingestion, storage,
and web. Responsibility packages inside ingestion are internal to that closed
module; no named interfaces or new application modules are introduced.

```text
com.cvcompass.backend
|-- BackendApplication
|-- ingestion
|   |-- controller   CvBatchController, CvDocumentController
|   |-- exception    IngestionExceptionHandler, BatchNotFoundException,
|   |                DocumentNotFoundException, UploadRejectedException
|   |-- service      CvBatchService, CvDocumentService
|   |-- dto          BatchDetails, BatchItem, DocumentMetadata, ImportResult, PageResult
|   |-- entity       BaseEntity, UpdatableEntity, Candidate, CvDocument,
|   |                CvExtraction, CvImportBatch, CvImportItem, CvProcessingJob
|   |-- repository   CandidateRepository, CvDocumentRepository, CvExtractionRepository,
|   |                CvImportBatchRepository, CvImportItemRepository, CvProcessingJobRepository
|   |-- enums        BatchStatus, DocumentStatus, ExtractionMethod, JobStatus
|   |-- config       BatchMultipartConfiguration
|   `-- upload       PdfUploadStream, PdfUploadValidation, UploadFilename
|-- storage          FileStorageService, StorageException, StorageKey, StoredFile
|   |-- config       StorageConfiguration, StorageProperties
|   `-- local        LocalFileStorageService, LocalStorageProperties
`-- web              ApiError, ApiResponse, FieldViolation
    |-- error        GlobalExceptionHandler
    `-- logging      CorrelationIdFilter
```

Controllers call services and return DTOs. The package-private ingestion advice
selects the controller package, preserving document/batch error codes, HTTP status,
correlation IDs and safe messages without a controller/exception dependency cycle.
Shared framework errors remain in web. JPA entities and repositories remain under
the existing application scanning root. BatchMultipartConfiguration and
PdfUploadStream stay package-private; PdfUploadValidation exposes only a borrowed
InputStream factory and the existing default limit. UploadFilename contains the
unchanged display-name validation shared by both services. Persistence callbacks
on CvDocumentService are private or package-private within service.

ImportResult is a standalone DTO with the same `batch` and `items` JSON components.
All endpoint, multipart, processing-order, partial-failure, transaction, rollback,
compensation, mapping and schema behavior is unchanged from M5 commit 60a1599.
No V1–V4 migration, runtime configuration or dependency is changed by this refactor.

BackendPackageStructureTests enforces responsibility placement, acyclic ingestion
subpackage dependencies, controller/persistence separation, internal implementation
visibility and advice scope. Existing ModulithArchitectureTests still verifies
exactly ingestion/storage/web and calls ApplicationModules.verify(). Run
`.\gradlew.bat clean check` (or `./gradlew clean check`) after a package move so stale
class files cannot hide scanning, duplicate bean, repository or serialization errors.

Focused M5 risk review: the configurable parser ceiling is at most 101 MiB, while
Tomcat's fixed 101 MiB drain budget is independent of lower configured limits.
This bounds draining; arbitrarily oversized bodies may still reset the connection.
DB interruption can leave PROCESSING batches; unknown commit outcomes can produce
file/metadata mismatches under compensation. These are the documented M5 limitations,
not new package-refactor behavior. No recovery, reconciliation or retry was added.
